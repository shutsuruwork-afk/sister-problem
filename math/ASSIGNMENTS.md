# セッション割り当てと衝突分析

`ROADMAP.md` の4ルートを、実際に別セッションへ配るための文書。
各セッションはコールドスタートなので、下のプロンプトは**単体で完結**するように書いてある。

---

## 見つかった衝突（と解消）

### 1. ルートA-1 と A-2 は同じカーネルを触る → **1セッションに統合**

`ROADMAP.md` では「16bit版の検証」と「11/12bitパッキングの試作」を別々の人に振っていたが、
どちらも同じ剰余幅・同じアトミック方式のコードを書くことになる。分けると確実に衝突する。
**統合して S1 とする。**

### 2. `kicky1618/oneesan-gpu` には push できない（read-only）

こちらのセッションから触れるのは `shutsuruwork-afk/sister-problem` だけ。
したがって S1 は「あちらの CUDA を書き換える」タスクではなく、
**「CPU参照実装＋Kaggle GPU マイクロベンチで数値を出し、あちらに渡せる形にする」**タスクになる。

### 3. このコンテナに GPU が無い → Kaggle が唯一の GPU

`KAGGLE_API_TOKEN` は環境変数にあり、`kaggle` パッケージは導入済み。
**Kaggle の GPU クォータ（週30時間程度）は S1 と S3 が取り合う。**
S1 を先に通し、S3 は当面 CPU で進める、という直列化で解消。

### 4. `math/src/` は全ルートの共有依存 → **読み取り専用**

`frontier.py` / `ranking.py` / `dense.py` / `hankel.py` / `symmetry.c` などは
検証済みの参照実装で、複数ルートが読む。**各セッションは自分の作業ディレクトリのみ書く。**
`math/src/` への変更が要る場合はロードマップ管理セッション（ここ）を経由する。

| セッション | 作業ディレクトリ | ブランチ |
|---|---|---|
| S1 狭剰余CRT | `math/narrow/` | `claude/narrow-residue-crt` |
| S2 厳密上界 | `math/bound/` | `claude/rigorous-bound-n28` |
| S3 CTMRG近似 | `math/tensor/` | `claude/ctmrg-approx` |
| S4 F_ρ 拡張 | `math/rho/` | `claude/rho-symmetric-count` |

### 5. 内容依存が1本だけある（ブロックはしない）

**S2 の出力（`a(28)` の厳密上界ビット数）は S1 の素数本数を決める。**
684 bit という現在の見積もりが縮めば S1 の総時間が減る。
ただし S1 の本命である「パッキングのスループット比」は S2 に依存しないので、
S1 はビット数をパラメータにして先行してよい。**直列化不要。**

### 6. 衝突しないもの

S2・S4 は CPU のみ・独立ファイル・他ルートのコードを読まない。
S3 は `math/src/hankel.py` を読むだけ。**実行資源も成果物も競合しない。**

## S1（最優先）狭剰余CRT — プロンプト

```
あなたの担当は「狭剰余CRT」ルート単独です。他のルートには触らないでください。

## 背景（確定している前提）

対象は OEIS A007764：(n+1)×(n+1) 格子点グラフの、左上から右下への自己回避経路の総数。
既知は a(27) まで。a(28) が未解決の最前線。

フロンティアDPの状態数には厳密な閉形式がある（このリポジトリの math/NOTES.md）：
  行境界 B(n) = M_{n+2} − M_{n+1}   （M_k は Motzkin 数）
実装で使われる main+blocked 表現の状態数は B(n) + B(n−1)：
  n=27 → 520,735,012,027
  n=28 → 1,489,362,193,002   （ちょうど 2.86 倍）

参考プロジェクト kicky1618/oneesan-gpu は 8×B300 ノードで n=27 を
uint32 剰余 × 約22素数の CRT で狙っている。n=27 の権威状態は 1,940 GiB、
8×B300 の予算は約 2,013 GiB（HBM 2,149 から LUT/scratch 実測 136 を引いた値）。

ここから決まること：
  n=28 が 8×B300 に載る条件は 11.6 bit/state 以下（reduced channel 適用なら 12.8）
  a(28) の厳密上界は約 684 bit（真値は 629 bit）
  → 11bit × 64素数 = 1,907 GiB で載る。12bit × 58素数 + reduced = 1,892 GiB。
  → 8bit は不可能。2^8 未満の素数を全部かき集めても 335 bit しかなく 684 bit に届かない。
  → 9bit（703 bit）が CRT の理論下限。

## あなたの成果物は2つ

1. CPU参照実装
   狭剰余（16 / 12 / 11 bit）の modular frontier DP を書き、複数素数の CRT で
   a(n) を厳密に再構成する。n ≤ 18 で既知値と一致することを示すこと。
   検証済みの参照実装が math/src/dp2.c（C・ハッシュ・64bit剰余）と
   math/src/dense.py（Python・密ランク配列）にある。読むのは自由、変更は不可。
   既知値の例：
     a(12) = 64528039343270018963357185158482118
     a(13) = 69450664761521361664274701548907358996488

2. Kaggle GPU でのスループット測定  ← こちらが本命
   11bit / 12bit の密パック配列に対する atomic 更新のスループットを、
   32bit atomic 比で測る。答えるべき問いは1つ：

     「サブバイト・パッキングでスループットは何倍落ちるか。1/3 以内に収まるか？」

   1/3 以内なら n=28 は 8×B300 に届く。落ちるなら NVL72 級を待つ判断になる。
   つまりこの数字がプロジェクト全体の意思決定を決める。

   実装の要点：11bit フィールドは 32/64bit ワードをまたぐので atomicCAS で包む必要がある。
   比較対象は最低でも (a) u32 atomicAdd、(b) 11bit 密パック + u64 atomicCAS、
   (c) 12bit 密パック、(d) 16bit。実DPのアクセスパターン（ほぼランダムな散布）を
   模したマイクロベンチで十分。競合率も振ること。

## 制約

- 書いてよいのは math/narrow/ 配下のみ。math/src/ は読み取り専用（他ルートが依存している）
- ブランチは claude/narrow-residue-crt。他ブランチに push しない
- このコンテナに GPU は無い。KAGGLE_API_TOKEN が環境変数にあり kaggle パッケージは導入済み
- kicky1618/oneesan-gpu は read-only。push できない。成果はこちらのリポジトリに置く
- Kaggle の GPU クォータは他セッションと共有。長時間ジョブの前に一声かけること

## 今回やること

まだ作業を始めないでください。
上を読んだうえで、自分の担当範囲・成果物・触ってはいけない場所を自分の言葉で要約し、
前提に疑問があれば挙げて、そこで止まってください。続行の指示は別途出します。
```

## S2 厳密上界 — プロンプト

```
あなたの担当は「a(28) の厳密上界を詰める」ルート単独です。他のルートには触らないでください。

## 背景

OEIS A007764（(n+1)×(n+1) 格子点グラフの角対角自己回避経路数）の a(28) を
CRT で厳密計算するとき、必要な素数の本数は「a(28) の厳密上界が何ビットか」で決まる。
状態数が巨大なので、素数1本 = 本番走行1回。1本減らせば数%〜が直接効く。

現在の構成（kicky1618/oneesan-gpu 由来、こちらでも独立に再導出済み）：
外周の s-t 経路 P0 を固定すると、任意の s-t 経路は T-join として
P0 XOR ∂F（F は n^2 個の有界面の部分集合）と一意に書ける。内点で P0 の次数は 0 なので、
面ビットが市松模様になると4本の接続辺が選ばれてしまい単純路になり得ない。
よって答えは「市松模様を含まない n×n 面ビット行列の個数」で上から抑えられる。

彼らの現行の評価は、高さ 9 以下の帯ごとに厳密な転送行列で数え、帯どうしの制約を
わざと無視して積を取る、というもの。n=27 で 9+9+9 の分割、633 bit。
真値は 585 bit なので 8% の緩み。

n=28 についてはこちらの見積もりが約 684 bit（真値 629 bit）。ただし
28 = 9+9+9+1 だと高さ1の帯が 1 bit/cell で弱い。7+7+7+7 との比較すら取っていない。

## あなたの成果物

1. n=28 に対する最良の帯分割を厳密に決める（高さの組み合わせを全部評価する）
2. さらに強い上界を狙う：n×n 全体に対する市松模様なし配置の個数 Z(n) は
   2^n 状態の転送行列 DP で厳密に計算できる（n=28 なら 2^28 = 2.7e8 状態）。
   多倍長で回すとメモリが厳しいので、主固有値からの厳密な上界でもよい。
   どちらでも「帯分割より何ビット縮むか」を数値で出すこと
3. 最終成果は1つの数：「a(28) の厳密上界は N bit」。そこから
   9/10/11/12/16 bit 剰余それぞれの必要素数本数の表を作る

## 検証

小さい n で「上界 ≥ 真値」を必ず確認すること。既知値：
  a(10) = 1568758030464750013214100
  a(12) = 64528039343270018963357185158482118
上界がこれを下回ったら構成が間違っている。

## 制約

- 書いてよいのは math/bound/ 配下のみ。math/src/ は読み取り専用
- ブランチは claude/rigorous-bound-n28
- CPU のみで完結する。GPU は不要（他セッションが Kaggle を使う）

## 今回やること

まだ作業を始めないでください。担当範囲を自分の言葉で要約し、疑問があれば挙げて止まってください。
```

## S3 CTMRG/MPS 近似 — プロンプト

```
あなたの担当は「テンソルネットワークによる高精度近似」ルート単独です。

## 背景（重要：厳密圧縮の道は既に閉じている）

このリポジトリで測定済みの2つの事実から出発すること（math/NEW-STRUCTURE.md, math/ROADMAP.md）：

1. DPベクトルをフロンティアで二分したときの厳密 Schmidt 階数は、
   GF(2^61−1) 上で W=4..11 のすべてで「きっちり最大値」だった（rank/max = 1.0000）。
   → 厳密な MPS 表現は存在しない。ここを再挑戦しないこと（math/src/schmidt.py が測定コード）

2. 特異値は速く減衰する（σ_32/σ_1 ≈ 1e-9）が、結合次元1単位あたりのビット数は
   W とともに単調に落ちる（W=6 で 2.64 → W=13 で 0.88）。
   684 bit を得るには χ ~ 2^80 が必要で、近似でも厳密列挙の代わりにはならない
   （math/src/svdecay.py）

したがってあなたの目的は「a(28) を厳密に出すこと」ではない。次の2つ：

## 成果物

1. 独立検証器（短期）
   χ が数千程度の MPS / CTMRG で a(n) を 10〜30 桁の精度で出す。
   まず a(10)〜a(16) の既知値に対して精度を実証すること。
   これは 8×B300 の本番走行 1 回よりはるかに安く、
   CRT 再構成が桁を間違えていないかの独立チェックになる。本番前に必ず通す位置づけ。

2. 成長定数 λ の改善（中期・単独で成果になる）
   角対角の正方形という幾何は Baxter の角転送行列（CTMRG）そのもので、
   SAW に対応する O(n=0) ループ模型は可積分。厳密列挙より桁違いに安く大きな n を扱える。
   文献値は λ ≈ 1.744550（Bousquet-Mélou–Guttmann–Jensen）。
   このリポジトリでは n ≤ 12 の厳密値だけから λ = 1.7444 を独立再現している。
   A007764 に CTMRG を当てた形跡は見当たらないので、桁を伸ばせれば独立の成果になる。

## 制約

- 書いてよいのは math/tensor/ 配下のみ。math/src/ は読み取り専用（hankel.py と frontier.py は読んでよい）
- ブランチは claude/ctmrg-approx
- Kaggle の GPU クォータは S1（狭剰余）が先に使う。当面 CPU で進め、GPU が要る段階で一声

特に「厳密圧縮は閉じている」を理解したことを示して、止まってください。
```

## S4 F_ρ の拡張 — プロンプト

```
あなたの担当は「180度回転対称な経路の数え上げ F_ρ(n) を大きな n へ延ばす」ルート単独です。
これは本線（a(28) の計算）には効きません。純粋に数学の未解決問題として面白い枠です。

## 背景

このリポジトリで確立済み（math/NEW-STRUCTURE.md）：

問題の対称群は G = {1, τ, ρ, ρτ} ≅ Z2 × Z2。
τ = 主対角反転、ρ = 180度回転、ρτ = 反対角反転。

格子は2部グラフで s と t が同色なので、すべての s-t 経路は偶数長＝頂点数は奇数。
よって経路を反転させる自己同型はちょうど1頂点を固定する。ここから：

- F_τ(n) = 0（n≥1）。τ対称な経路は1つも存在しない（証明済み）
- F_ρ(n) = 0（n 奇数）。n 偶数なら ρ対称な経路は必ず中心を通る
- ρτ対称な経路は反対角線とちょうど1点で交わる（証明済み）

ρτ の方は、この構造定理から三角形DPに落ちて解けている。新しい数列が出た：
  F_ρτ(n) = 2, 4, 12, 48, 288, 2768, 45408, 1289000, 63234984, 5356226560,
            784701065224, 199206933174016, 87751261902772392   (n=1..13)
n ≤ 6 は総当たりと完全一致（math/src/antidiag.py, math/src/symmetry.c）。

## 未解決なのが F_ρ

総当たりで得られているのは F_ρ(2)=4, F_ρ(4)=120, F_ρ(6)=32916 のみ。
ρ の固定点は中心1点だけなので、ρτ のような平面的な切断が取れない。

定式化はできる：ρ対称な経路 P は中心 c を通り、P = A + c + reverse(ρ(A))、
A は s から c の隣接点への自己回避路で A ∩ ρ(A) = ∅。
これは商グラフ 格子/ρ 上の自己回避路と1対1対応する。
しかし商グラフでは連結性が非交差でなくなるため、フロンティアDPの状態が
非交差マッチングではなく一般の集合分割になり、状態空間が悪化する。

## 成果物

1. F_ρ(n) を n=8, 10, 12, ... へ延ばす方法を見つけて実装する
   （商グラフの向き付け、別の切断、包除、何でもよい）
2. 総当たりとの一致を n ≤ 6 で必ず確認すること

## 検証できる予言が1つある

合同式 a(n) ≡ F_ρ(n) + F_ρτ(n) (mod 4) が成り立つ（Burnside、n≤6 で確認済み）。
a(8) ≡ 2 (mod 4) かつ F_ρτ(8) = 1289000 ≡ 0 (mod 4) なので、
  **F_ρ(8) ≡ 2 (mod 4)** が予言される。
実装が正しければこれを満たすはず。満たさなければどこかが間違っている。

- ブランチは claude/rho-symmetric-count
- CPU のみ
```
