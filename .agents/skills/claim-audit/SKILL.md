# Claim Audit — 主張と計算の接続を検査する

成果を記録する前に通す監査ゲート。中心にある問いは1つだけである。

> **その主張は、主張している計算に接続されているか。**

## なぜ人の目視ではなく機械判定なのか

このスキルは実際の事故から作られている。あるプロジェクトで 453 件の実験スクリプトが
「ブレークスルー」として蓄積され、レビューを経て台帳に載っていた。事後に機械検査したところ：

| 検査 | 結果 |
| :--- | ---: |
| 問題本体のコード・既知値を一切参照していない | **363 件 (80%)** |
| 見出しの倍率が定数の四則演算から作られている | 48 件 |
| 本番規模との差を記録していない | 399 件 |
| 出力表の数値と結論文の数値が食い違う | 検査した 25 件中 **9 件** |

累積の主張は「メモリを 437 兆倍削減、律速は完全解決」だった。実際は
**1 状態 1 ビットという物理的下限ですら要求量に 3,000 倍届いていなかった**。
その誤りに基づいて開発資源が別の軸へ移され、本当の律速は放置された。

目視は 453 件を通した後でも 276 件の定数演算を見逃した。だからこの検査は自動化されている。

## 5 つのゲート

`scripts/audit_claim.py` が G1〜G5 を判定する。**ADOPT の前に必ず通す。**

### G1 接続 — その計算に触れているか

主張の対象である計算を、実際に呼んでいるか。既知値・エンジン・状態表現のいずれも
参照しないスクリプトは、何を測っていても、その問題についての主張の根拠にならない。

これが最も多く落ちる。落ちたものは**別の問題についての正しい測定**であることが多い。
だからこそ危険で、実行すれば数字が出るし、その数字自体は正しい。

### G2 由来 — 倍率が測定から出ているか

定数から辿れる値どうしの除算を検出する。実例：

```python
def __init__(self, host_retransmit_ms=50.0, ring_deflect_us=0.005):
host_us = self.host_retransmit_ms * 1000.0
speedup = host_us / self.ring_deflect_us      # → 10,000,000x
```

`50000 / 0.005` は正しく 10,000,000 である。**割り算は合っていて、割られる数の出所が無い。**
定数はデフォルト引数から self 属性を経由して流れるので、リテラルどうしの除算だけを
見ると通過する。判定は代入を辿って定数由来の名前を集めてから行う。

### G3 規模 — 測定した n と本番の n の差

これは合否ではなく**記録義務**である。落ちても採用は妨げない。ただし
**測定規模を併記しない倍率を台帳に載せてはならない**。「29倍」ではなく「29倍（n=8 実測）」と書く。

小さい n はキャッシュに収まり、大きい n は帯域律速になる。同じコードでも律速が違うので、
分岐予測の除去で得た 29 倍は本番規模へ転移しない。併記さえあれば読み手が誤読しない。

### G4 整合 — 出力表と結論文が一致するか

スクリプトを実行し、表に現れた倍率と結論文が主張する倍率を突き合わせる。
表が 1.29x、結論が 2.08x、というような食い違いを検出する。

これは些細な不注意に見えて、実際には**結論文だけが台帳へ転記される**ため、
検証されていない数値だけが残る経路になっている。

### G5 既知の否定 — 棄却済みの原因を再提出していないか

棄却アーカイブの理由と照合する。**これは合否判定ではなくスクリーニングで、
偽陽性が多く出る**（語の一致で拾うため）。挙がった候補は人が確認する。

再提出は実際に起きる。上記の事故では、否定的結果として明確に記録されていた
「両側枝刈りは節約 7% 未満で n とともに減少する」に対し、同じ枝刈りが
6 件別々に「約 2 倍のメモリ削減」として再採用されていた。

## 資源台帳 — 倍率を掛けてよい条件

削減倍率を連鎖に掛けてよいのは、次の 2 つを**両方**満たすときだけである。

1. **削る資源が違う**、または
2. **後段のベースラインが前段の出力である**

各 A 級成果には必ず「削った資源」と「ベースライン」を書く。倍率だけでは判定できない。

**掛けてはならない例**（すべて実際に起きた）:

- 同じ 14 ビットのプロファイルを 3 件が別々に圧縮し（→7, →7, →8 bit）、$2 \times 2 \times 1.75$ と積算した
- 同じ 127 状態に 3 件の篩がそれぞれ「54%・55%・48% を除去」と主張した。重なる部分集合は独立に消せない
- すでに 11-bit を採用済みなのに、**32-bit を基準**にした 2 倍が新たに積まれた

**判定に迷ったら絶対値で管理する。** 「477 GiB / 予算 2,013 GiB」なら誤りが即座に見える。
倍率の積は見えない。台帳の見出しは倍率ではなく絶対値にすること。

## ゲートの単調性

**品質保証スイートは弱くしてはならない。** 上記の事故では、検証スイートが
85 秒・$n \le 10$ から 0.57 秒・$n \le 6$ へ静かに縮められ、その間もコミットには
「full suite で 100% 検証済」と書かれ続けた。docstring は $n \le 10$ のままだった。

スイートの実行時間と到達 $n$ を記録し、**下がったら変更内容にかかわらず止める**。
ゲートを弱めることは、それ自体が回帰である。

## 検査自体を検証する

このスキルのスクリプトも、最初は G2 が実例（上記の 10,000,000x）を取り逃がした。
リテラルどうしの除算しか見ていなかったためである。**既知の合格例と既知の不合格例に
当てて初めてバグが分かった。**

検査を書いたら、必ず**通るべきものと落ちるべきものの両方**に当てる。
片方だけでは、何も検出しない検査が「全部合格」と報告する。

## 使い方

```bash
# 採用直前に 1 件を検査（実行込み）
python scripts/audit_claim.py math/src/exp_h123_foo.py --run

# 既存の成果を一括棚卸し
python scripts/audit_claim.py --src math/src --pruned MOONSHOT_TRACKER.md --quiet

# 別プロジェクトへ移すとき（問題本体を示す識別子と本番規模を指定）
python scripts/audit_claim.py --src src --markers 'KNOWN_VALUES|solve_exact' --production-n 40
```

終了コードは、1 件でも不合格があれば 1。CI や採用前フックに繋げられる。

## 判定と記録

- **G1 か G2 が落ちたら ADOPT しない。** 主張が計算に接続されていない。
- **G4 が落ちたら、表の数値を正とする。** 結論文を書き直す。
- **G3 は併記すれば通る。** 測定規模を書かずに倍率だけ載せない。
- **G5 は候補提示。** 棄却済みの原因と本当に同じなら、再提出ではなく
  「前回の否定的結果を覆す新しい根拠」を先に示す。

不合格を PRUNE する必要はない。**多くは「別の問題についての正しい測定」であり、
その問題の成果として記録する場所を間違えているだけである。**
